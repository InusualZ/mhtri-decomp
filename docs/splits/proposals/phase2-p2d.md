## 2. What the evidence is

Per symbol: the units whose decoded text reads it (a pool literal only by a load), the units whose functions its code pointers hit (a jump table's
case labels too), and the units that read or hold the data symbols that point at it. A symbol named by one unit of the run's candidates is an
**anchor**; the heaviest link-order-monotone chain of anchors is kept (the rest are conflicts), consecutive anchors of one unit make a piece, and the
symbols between a piece's anchors are the unit's. Between two pieces nothing is given away: that interval is `unowned_data` with the candidates
(the units between the two pieces in link order). The only extensions without an anchor are forced by one range per section: the head of a run
whose first piece is its predecessor's, the tail of a run whose last piece is its successor's.

The attached pieces are consistent: **2 conflicts in 3,862 symbols** (anchors that break the link-order chain) - `lbl_805E7180` and `lbl_805E7B60`,
`.data` objects whose only reader is a function of `ef/eft050` (`fn_8033F270`'s `lis`/`addi` passes the address of the first one on), sitting between
`lb_companion_ui`'s and `eft_slot`'s anchors (an extern use of the neighbour's table, or an edge one function off); both are open questions with `callers.py` commands. The 2 conflicts of the first pass
(`jumptable_805E0EA0`, `lbl_805E1ED0`, the interleave of section 4) disappear with the fold.

## 6. Residuals and gaps

* **A sole reader is taken for the owner.** A global read by exactly one unit is attached to it; a TU that defines an object it never reads (only the
  rest of the program does) would be wrong. The monotone chain catches the cases that interleave (2 conflicts), not the ones that stay in order.
  The pointer evidence (`P`/`D`, 897 symbols, grade medium unless a direct anchor is next to it) is weaker: a table of unit X that points at a global
  of another unit is read as "belongs to X"; only pieces with three such anchors are attached without a direct one.
* **Shared objects are not given.** An object read by many units (`.bss` 0x806BF530 / 0x806BE340, 0x2EB8 / 0xBE0 B; the `.sbss` words) is deferred
  with its readers: signal 5 (bss in text order) gives the interval, not the owner. The owner is whichever candidate defines it.
* **The `pool` invariant is a heuristic over first-use order** (section 3): two new FAILs are checker noise on correct ownership; the two literals can
  be inspected with `dataattach.py --unit cockpit_quest --section .sdata2`. `splitcheck` now judges the order per section (commit
  `tools/splitcheck: judge pool first-use order inside one section ...`), which `hud/layout`, `menu/menu_infomation` and `menu/menu_result` needed
  (a unit owning `.sdata` strings and `.sdata2` literals compared the last string with the first literal).
* **A registered data-only unit can be a fragment** of the TU before it; the engine detects it where that unit's anchors lie on both sides
  (`cockpit_icon_data`), and a data-only unit after a unit that does not read around it stays a candidate owner (`hud/fn_80382310`, band e).
* **Cross-lane overlap.** The three `.sdata2` runs include the pieces of units outside the window (`enemy/fn_80387844` .. `lobby/lb_quest_screen`, whose
  `.sdata2` is unowned and whose last owner is `ef/eft053`); they are given here because the run belongs to the lane of its last owner.
  `unowned_data` candidate lists name units of band e (`fn_80382310`, `fn_80383148`).
* **Not done:** `.ctors`/`.dtors`/`extab`/`extabindex`/`.init` need nothing in the window (derived from the text cuts); `__FILE__` strings (signal 7)
  and the `.data` emission-order seams (signal 2) decided no range; no text cut other than the fold was proposed.
