# How the Wii/1.3 facts were derived

This is the evidence trail for the `Wii/1.3` row in `../versions.py` and for
the three record layouts the port added to `../mwcc_debugger.py`.  It is here
because the whole difficulty of supporting a new compiler build is *finding*
these numbers, and because they must be re-derivable when the build changes.

The tools in this directory are development-time only, and (except
`extract_upstream_tables.py`) need `pip install capstone`; the shipped
debugger itself has no dependencies beyond gdb and the repository's own
`tools/lib` (the one PE reader, `tools/lib/binary/pe.py`, which these tools
use too).

## The lever: Metrowerks' own symbol table

Every **Wii** compiler in `build/compilers/Wii/*` ships a CodeView `NB11`
symbol blob: the Metrowerks linker appends it after the last PE section and
points the debug directory at it (type 2).  It names ~5700-5800 functions and
globals with a section index and an offset, which converts directly to an RVA:

```
$ python locate/dissect.py syms build/compilers/Wii/1.3/mwcceppc.exe '^_(CodeGen|opcodeinfo|pcbasic)'
0006bef0  0046bef0  _CodeGen_Generator   .text
002f3b9a  006f3b9a  _opcodeinfo          .data
00376edc  00776edc  _pcbasicblocks       .bss
```

The **GC** compilers do not have it (checked: all 21 of them), which is why the
GC facts had to be reverse-engineered the hard way and why Wii support is
tractable where GC support is not.

`versions.py` reads this blob itself (`Pe.symbols()`) and `build()` re-checks
the Wii/1.3 row against it every run, so a table that describes a different
binary fails loudly instead of dumping plausible-looking garbage.

## The facts

| field | value (RVA) | how it was derived |
|---|---|---|
| `codegen_start_addr` | `0x6c02f` | `_CodeGen_Generator` (0x6bef0) stores the current function (`mov [0x777000], eax` at 0x6c02a); this is the next instruction, so the object is live. |
| `codegen_end_addr` | `0x6cea1` | the shared exit path of the same function (`add esp, 0x50` after the heap-report branch, before `ret` at 0x6cea8). Verified to be hit on every function with a gdb run. |
| `gfunction_addr` | `0x377000` | symbol `_gFunction`; also the store site above. |
| `cmangler_getlinkname_addr` | `0x16f7f0` | symbol `_CMangler_GetLinkName`. |
| `nodenames_addr` / `_size` | `0x33a054` / 89 | `_IRO_InitializeNodeNamesArray` (0x1de320) fills exactly 89 slots (its loop bound is `cmp ecx, 0x51` plus the tail write) and then stores pointers to the `EPOSTINC`/`EADDCONST`/... strings. Slot 0 is `EPOSTINC` and slot 66 is `EINFO`, the same numbering as GC/1.1 (checked against the GC/1.1 array at 0x561cb4). |
| `ast_breakpoints` | `0x6c183`, `0x6c19b`, `0x6c1a0` | the three places inside `_CodeGen_Generator` where a statement list is the top of stack: `push ebx; push [esp+0x48]; call _COpt_Optimizer` (0x6c182-0x6c187, so at 0x6c183 `[esp]` is the pre-optimization list) and the `push edi; call _expandTOCreferences` pair (0x6c19a/0x6c19b, with 0x6c1a0 its return address). The last two are exactly 5 bytes apart - one `call` - which is the invariant the GC rows show (`final-code == after-optimizations + 5`). |
| `opcodeinfo_addr` / `_size` / `_stride` | `0x2f3b9a` / 1577 / `0x16` | symbol `_opcodeinfo`; the indexer is `lea ecx,[edx+edx*4]; add ecx,ecx; add ecx,edx; mov eax,[ecx*2+0x6f3b9a]` = 22 bytes per entry. The bound: `_pcodestats_dump_opcode` compares an opcode against `0x629` (1577), and `(0x2fc320 - 0x2f3b9a) / 0x16 == 1577` exactly - the next symbol, `_vletoppc`, starts where the table ends. |
| `pcbasicblocks_addr` | `0x376edc` | symbol `_pcbasicblocks`; `_makepcblock` writes it for the first block. |
| `pcode_breakpoints` | 82 entries | generated by `pass_points.py` (see below). |
| `regalloc_breakpoint_addr` | `0x1b9947` | just after `call 0x5b9b10` in `_colorinstructions`: the colorer has written every physical register and its priority list is still on the stack. |
| `interferencegraph_addr` | `0x37814c` | symbol `_interferencegraph`. |
| `used_virtual_registers_*` | `0x37d578` (GPR) / `0x37d574` (FPR) | symbol `_used_virtual_registers` (0x37d568) indexed by colouring class: `mov ecx,[eax*4 + 0x77d568]` in `_colorinstructions`, with class 4 = GPR and 3 = FPR (the same numbering `coloring_classes` records). |
| `coloring_class_addr` | `0x3994b2` | symbol `_coloring_class`; written by the class loop in `_colorinstructions` (0x1b9839). |
| `supports_ast` | `False` | the frontend records are not derived (below). |
| `supports_variables` | `False` | not derived; upstream only ever had it for GC/1.1. |

### `pcode_breakpoints`

`pass_points.py` disassembles the three pass drivers and takes the **return
address** of every `call <named pass>`:

```
python locate/pass_points.py build/compilers/Wii/1.3/mwcceppc.exe
```

* `_globallyoptimizepcode` (0x1b8de0) - the -O2/-O3/-O4 propagation and
  peephole pipeline (this build has one driver with opt-level branches, where
  the GC builds have one function per level),
* `_CodeGen_Generator` (0x6bef0) - the shared passes: initial code, regalloc,
  prologue/epilogue, scheduling, peephole, assembly,
* `_colorinstructions` (0x1b9810) - the interference-graph build.

That is the same idea as upstream's hand-picked "just after the flag is
checked" addresses, but derived rather than transcribed, and it is why the
Wii/1.3 list has 82 entries where GC/2.6 has 53.  A return address is a safe
dump point because `print_pcode` only reads the global block list, and every
one of these points is after a pass has finished with it.

## The record layouts

Wii/1.3 is **not** the GC/1.3.2 layout.  It is a later core (0x272d6a bytes of
`.text` against GC/1.3.2's 0x17c5bc) with different records throughout, so each
one was derived separately.  All three were confirmed with a live gdb probe
(the recipe is at the bottom of this file).

**Object record** (`MwccObject._load_wii13`) - from `_CMangler_GetLinkName`
(0x16f7f0) plus probing:

```
+0x02  u8   datatype (3 = FUNC, 4 = VFUNC)
+0x0C  u32  -> name node; the string is at +0x0A of that node
+0x24  u32  -> type node (size at +2)
+0x48  u32  -> *mangled* name node, computed lazily
```

`_CMangler_GetLinkName` dispatches on the datatype through a jump table at
0x6813a4: datatype 3/4 returns the cached pointer at `+0x48`, everything else
returns `+0x0C`.  The cache is **empty** while `CodeGen_Generator` is running,
and calling the mangler from the `codegen_start` breakpoint aborts this build
with `internal compiler error ... in file 'CMangler.c' line: 1128`.  The port
therefore matches functions by their *source* name and documents that.

**PCode instruction** (`load_pcode_wii13`) - from `_vformatpcode` (0x5ae160),
which allocates `(nargs + 6) * 0x0E + 0x2C` bytes and stores
`[eax+0x28] = op`, `[eax+0x2A] = nargs`, and from `_appendpcode` (0x5a0ba0),
which links `[eax] = next`, `[eax+4] = prev`, `[eax+8] = owning block`:

```
+0x00 next      +0x04 prev      +0x08 block     +0x20 statement
+0x28 u16 op    +0x2A u16 arg count             +0x2C args, 0x0E each
```

**PCode operand** (0x0E bytes) - read off a live dump of a compiler run
(probe below); the decoded field values are what made the layout unambiguous:

```
+0x0 kind  0=register 1/2=immediate 4=fixup 6=label 8=placeholder
+0x1 class register file when kind==0: 4=GPR 3=FPR 1=CR field 0=special
+0x2 u16   operand value for kinds 1/2/4/6; use/def flag (1/2) for a register
+0x4 s16   register number (virtual >= 32 before regalloc); label id for kind 6
```

The probe that pinned this down printed, for the first block of
`fn_8004C9A0`:

```
 5 op=103 argc=5 | a0 k=0 c=4 f=0002 v=37 | a1 k=0 c=4 f=0001 v=33
                 | a2 k=2 c=0 f=0000 v=0  | a3 k=2 c=0 f=0010 v=0
                 | a4 k=2 c=0 f=001f v=0
```

`op=103` is `RLWINM`, and `f` at `+2` gives `0, 16, 31` - the `clrlwi r0,r4,16`
this function emits.  (Reading `+4` instead gives zeros, which is what the
first attempt did; that is why the dump now carries both fields.)

**Basic block** (`load_block_wii13`) - from `_makepcblock` (0x5a0e20), which
allocates 0x2E bytes, stores the current line at `+0x24` and the index at
`+0x1C`, and from `_appendpcode`, which keeps head `+0x14`, tail `+0x18` and
the instruction count `+0x28`.

**Interference-graph node** (`load_ignode_wii13`) - from `_colorinstructions`
and `_pickcolor`'s caller, which address a node as `[0x77814c] + reg * 0x20`
(0x5b9be5, 0x5b9d0f), i.e. a **flat array of records**, not the GC builds'
array of pointers:

```
+0x00 next   +0x04 object   +0x0C cost
+0x10 u16 virtual reg   +0x12 u16 physical reg   +0x14 u16 flags
+0x16 u16 degree        +0x18 u16 second counter +0x1C interference list
```

`_makeinterfere` (0x23fc60) shows the interference list is a list of *pairs*:
each 0x10-byte record is threaded into two lists at once (`[rec+4]` is the next
pointer for endpoint A, `[rec+8]` for endpoint B, `[rec+0x0C]`/`[rec+0x0E]` are
the two endpoints), which is why `neighbors_wii13` picks the linker by
comparing the node's own virtual register with the pair's second endpoint -
that is exactly what 0x5b9bc0..0x5b9c2d does.

## Not derived (and said so at runtime)

* **Frontend records** - `ENode`, `Statement`, `Type`.  The AST breakpoints and
  the node-name table are located, but the record layouts are not, so the tool
  announced and skipped the AST dumps rather than printing garbage.
* Block successors/predecessors/label lists, and per-instruction line numbers.
* The `variables.txt` frame layout.

## Repeating this for another Wii build

1. `python locate/dissect.py syms <exe> '^_CodeGen_Generator$'` and friends -
   the data half of a row is then a symbol lookup.
2. `python locate/pass_points.py <exe>` - after teaching it that build's driver
   addresses, if they moved.
3. For the records, run the compiler under gdb and print the fields (this is
   the probe that produced the operand table above; put it in a file and
   `gdb -batch -nx -x probe.gdb`):

```
file C:/.../mwcceppc.exe
set args <the bare mwcceppc command line>
break *0x46cb92                 # any pcode_breakpoint, e.g. initial code
run
set $blk = *(unsigned int*)0x776edc          # pcbasicblocks
set $i   = *(unsigned int*)($blk+0x14)       # first instruction
while $i != 0
  printf "%p op=%d argc=%d\n", $i, *(unsigned short*)($i+0x28), *(unsigned short*)($i+0x2a)
  set $i = *(unsigned int*)$i
end
```

4. `python locate/verify_pcode.py <backend dump> <object>` to prove the new
   layout against the object before trusting it.  It classifies the dump first,
   so use the **last** dump of a run for the pass/fail proof (`MATCH`, or `FAIL`
   with the first divergence) and any earlier one for a `PASS-DELTA` - the
   changes from that pass forward, which is how a residual gets attributed to a
   pass.  `locate/verify_pcode_selftest.py` pins both with fixtures.

Note that the *other* Wii builds (1.5, 1.6, 1.7, 1.1, 1.0, 1.0RC1, 1.0a,
0x4201_127) all carry the same kind of symbol blob, so this path generalises;
the 1.3-specific numbers (and the 0x20 stride, 0x0E operand size) would have to
be re-checked per build.
